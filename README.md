Copy this folder to a repository of your own, `git init`, and start from **M1** of
[Lab 01](../lab-01-a-box-of-bytes.md). It builds and runs as-is.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/ember
```

## Why a skeleton exists

Lab 1 is about **bytes and types**. It is not about `while` loops, splitting a
string into words, or `std::setw` — you meet those properly in Labs 4, 5 and 7.
So the parts that need them are given to you, fully written and commented. You
read those. You write the four small things that *are* Lab 1.

### 1. Переповнення Byte


Після `set 0 255` і `inc 0` значення стало `0`.
`Byte` зберігає значення від 0 до 255, тому збільшення 255 дає перехід
через межу до 0. Переповнення знакового `int` відрізняється: це невизначена
поведінка, яку виявляє UBSan.

```txt
ember> set 0 255
ember> inc 0
ember> get 0
0 0x0 0b00000000 '.'
```

### 2. Float числа

`0.1 + 0.1 + 0.1 == 0.3` повертає `false`, тому що десяткові дроби
на кшталт `0.1` зазвичай неможливо точно представити у двійковому форматі
`double`. Сума виходить дуже близькою до `0.3`, але не обов’язково дорівнює їй.

```txt
c++ -std=c++17 -Wall -Wextra -Werror scratch.cpp -o scratch && ./scratch
result = 0.30000000000000004
result == 0.3: false
```

### 3. C-рядок 
```txt
ember> set 0 65
ember> set 1 66 
ember> set 2 0
ember> dump
0000  41 42 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |AB..............|
0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

### 4. Неініціалізована памʼять 

Після видалення `{}` з `Byte data[MEM_SIZE]{}` команда `dump` виводить
невизначені значення. Потім дужки `{}` було повернуто на місце, оскільки
читання неініціалізованої пам’яті є невизначеною поведінкою.

```txt
ember> dump
0000  d0 64 e7 6a 01 00 00 00 40 d3 ba fb 01 00 00 00  |.d.j....@.......|
0010  c0 55 e7 6a 01 00 00 00 14 a6 0a 8f 01 00 00 00  |.U.j............|
0020  f4 87 62 eb 02 00 00 00 e0 b0 62 eb 02 00 00 00  |..b.......b.....|
```



### Чому `Byte` — це `std::uint8_t`, а не `int`

Клітинка пам’яті `ember` має бути рівно одним байтом на кожній машині.
`std::uint8_t` гарантує розмір 8 біт і зберігає значення від 0 до 255.
Розмір `int` стандартом не фіксований: він може відрізнятися на різних
платформах і зазвичай займає більше ніж один байт. Тому `int` не підходить
для представлення однієї клітинки пам’яті.


### Stretch: `set16` і порядок байтів

```txt
ember> set16 0 0x1234
ember> dump
0000  34 12 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |4...............|
```

Число `0x1234` зберігається як `34 12`, тому програма використовує
порядок байтів little-endian: молодший байт записується першим.




# LAB 2 ------------------------------------------------------



## M1 — ALU як функції, перевірені руками

Цей блок — перший крок Lab 2: операції над `uint8_t` мають бути не просто
“задумом”, а реально перевіреними на прикладах.

### 1. ADD: 200 + 100

```txt
ember> alu add 200 100
result=44 Z=0 N=0 C=1
```

Пояснення:
- `200 + 100 = 300`
- `300 = 256 + 44`
- у 8-мі бітному байті `256` — це перенесення через межу байта, тобто `C = 1`
- результат в межах байта: `44`
- `Z = 0`, бо результат не нульовий
- `N = 0`, бо старший біт результату не увімкнений

### 2. AND: перевірка бітових масок

```txt
ember> alu and 13 9
result=9 Z=0 N=0 C=0
```

Пояснення:
- `13` = `00001101`
- `9` = `00001001`
- `13 & 9` = `00001001` = `9`
- `AND` не дає перенесення, тому `C = 0`

### 3. SHL: зсув вліво

```txt
ember> alu shl 3 0
result=6 Z=0 N=0 C=0
```

Пояснення:
- `3` = `00000011`
- `3 << 1` = `00000110` = `6`
- немає перенесення за межу байта, тому `C = 0`

Ще один приклад з перенесенням:

```txt
ember> alu shl 128 0
result=0 Z=1 N=0 C=1
```

Тут:
- `128` = `10000000`
- при зсуві вліво старший біт вилітає за межу байта
- результат стає `0`, прапорець `Z = 1`
- є перенесення, тому `C = 1`

### Чому це важливо

ALU у процесорі працює не “з числами як у математиці”, а з бітом і прапорцями:
- `C` показує, чи був перенос через 8-й біт
- `N` показує, чи був встановлений старший біт
- `Z` показує, чи результат дорівнює нулю

Саме ці прапорці потім використовує `step()` і `CPU` для виконання інструкцій.






## M2 — закодувати, завантажити, `step`

Після того, як ALU працює, наступний крок — запустити його в рамках процесора.

### 1. Присвоїти регістрам значення

```txt
ember> reg a 200
ember> reg b 100
ember> regs
PC=0 A=200 B=100 Z=0 N=0 C=0
```

Тут видно, що регістри `A` і `B` вже містять потрібні байти, а `PC` стоїть на адресі 0.

### 2. Завантажити програму в пам'ять

Ми ставимо в пам'ять кілька байтів:
- `ADD` = `0x10`
- `HALT` = `0x00`

```txt
ember> set 0 16
ember> set 1 0
```

Тобто в пам'яті лежить такий фрагмент:

```txt
mem[0] = 0x10   ; ADD
mem[1] = 0x00   ; HALT
```

### 3. Виконати одну інструкцію через `step`

```txt
ember> step
ember> regs
PC=1 A=44 B=100 Z=0 N=0 C=1
```

Що відбувається:
- `step()` читає байт з `PC`
- бачить `0x10` — це `ADD`
- бере `A` і `B`
- виконує `A = A + B`
- `A` стає `44`
- прапорці оновлюються: `C=1`, `Z=0`, `N=0`
- `PC` зсувається на наступну інструкцію

### 4. Виконати `HALT`

```txt
ember> step
ember> regs
PC=2 A=44 B=100 Z=0 N=0 C=1
```

Після другого `step`:
- в `PC` лежить наступна адреса
- програма бачить `HALT`
- встановлюється ознака зупинки `halted = true`
- наступні виклики `step` більше не виконують інструкції, а пишуть:

```txt
halted
```

### 5. Чому `PC` зміщується так

У базовому варіанті інструкція `ADD` займає 1 байт. Тому після виконання `ADD`:
- `PC` збільшується на `1`
- потім наступний `step` читає байт `HALT` і зупиняє процесор

У майбутніх лабах, коли з'являться інструкції з операндами, `PC` буде збільшуватися на більше, ніж 1, і цей механізм стане більш явним.

### 6. Що вважати готовим для M2

- `reg a ...` і `reg b ...` встановлюють значення регістрів
- через `set` можна записувати байти програми в пам'ять
- `step` виконує одну інструкцію
- `HALT` зупиняє виконання
- `regs` показує поточний стан: `PC A B Z N C`
- приклад `ADD`/`HALT` працює і легко відтворюється







## M3 — програма, яку видно

Після того, як `step` працює, наступний крок — показати, що процесор виконує не одну операцію, а справжню програму з пам'яті.

### 1. Приклад: `AND` + `HALT`

```txt
ember> reg a 7
ember> reg b 1
ember> set 0 18
ember> set 1 0
ember> regs
PC=0 A=7 B=1 Z=0 N=0 C=0
ember> step
ember> step
ember> regs
PC=2 A=1 B=1 Z=0 N=0 C=0
```

Тут:
- `A = 7`
- `B = 1`
- у пам'яті лежить:
  - `mem[0] = 0x12` = `AND`
  - `mem[1] = 0x00` = `HALT`

Перший `step`:
- читає `mem[0]`
- виконує `A = A & B`
- `7 & 1 = 1`
- `PC` зсувається на `1`

Другий `step`:
- читає `mem[1]`
- бачить `HALT`
- зупиняє процесор

Трасування:

```txt
PC=0, mem[PC]=0x12 -> A=1, Z=0, N=0, C=0
PC=1, mem[PC]=0x00 -> halted
```

### 2. Власна програма з трьох інструкцій

Приклад з `SHL`:
`SHL` — це зсув бітів регістра `A` вліво на один розряд.

```txt
ember> reg a 1
ember> set 0 22
ember> set 1 22
ember> set 2 0
ember> regs
PC=0 A=1 B=0 Z=0 N=0 C=0
ember> step
ember> regs
PC=1 A=2 B=0 Z=0 N=0 C=0
ember> step
ember> regs
PC=2 A=4 B=0 Z=0 N=0 C=0
ember> step
ember> regs
PC=3 A=4 B=0 Z=0 N=0 C=0
ember> step
halted
```

Тут:
- `A = 1`
- `mem[0] = 0x16` = `SHL`
- `mem[1] = 0x16` = `SHL`
- `mem[2] = 0x00` = `HALT`
- третій `step` виконує `HALT`: `PC` стає `3`, процесор зупиняється


Початковий стан: `PC=0`, тобто наступна інструкція буде прочитана з `mem[0]`.

Перший `step` читає `mem[0]` (`SHL`): значення `A` зсувається вліво з `1` до `2`, а `PC` переходить на `1`.

Другий `step` читає `mem[1]` (`SHL`): `A` зсувається з `2` до `4`, а `PC` переходить на `2`.

Третій `step` читає `mem[2]` (`HALT`). Після цього `PC` дорівнює `3`, бо адреса інструкції `HALT` вже пройдена, і процесор позначає себе зупиненим. Регістри показують `PC=3 A=4 B=0 Z=0 N=0 C=0`.

Четвертий `step` не виконує нову інструкцію: процесор уже зупинений, тому друкує `halted`.

Трасування: `PC` у кожному рядку нижче — адреса інструкції **до** її виконання. Після виконання `HALT` лічильник переходить з `2` на `3`.


```txt
PC=0, mem[PC]=0x16 (SHL) -> A=2, Z=0, N=0, C=0; PC=1
PC=1, mem[PC]=0x16 (SHL) -> A=4, Z=0, N=0, C=0; PC=2
PC=2, mem[PC]=0x00 (HALT) -> A=4, Z=0, N=0, C=0; PC=3, halted=true
після цього PC=3; ще один step -> halted (PC і регістри не змінюються)
```



## M4 — розбирати опкод масками

У M4 `step()` не порівнює весь байт із окремим кодом кожної інструкції.
Спочатку `decode(Byte)` розкладає його на поля, а `step()` обирає групу
інструкцій і потім конкретний індекс усередині цієї групи. Реалізація декодера
та обидва `switch` розміщені в `src/cpu.cpp`.

### 1. Розкласти байт на поля

За форматом §3 байт має три поля:

```txt
opcode:4 | dest:2 | src:2
```

У `cpu.cpp` поля виділяються масками та зсувами:

```cpp
group = (instruction >> 4) & 0x0F;
dest  = (instruction >> 2) & 0x03;
src   =  instruction       & 0x03;
index = (dest << 2) | src;
```

Наприклад, `0x16` у двійковому вигляді — `0001 0110`:

```txt
group = 0001 = 1
dest  =   01 = 1
src   =   10 = 2
index = 01 10 = 6
```

Отже, `0x16` належить до групи `0x1` та має індекс `6`, тобто це `SHL`.
У поточному прототипі `dest` і `src` поки не вибирають окремі регістри — їх
об'єднання утворює молодший півбайт `index`, якого потребують чинні коди ISA.

Перевірка з §3: байт `0b1011'10'01` декодується як `group=11`, `dest=2`,
`src=1`.

### Пастка пріоритету з notes, §3

У C++ `==` має вищий пріоритет, ніж побітовий `&`. Тому вираз
`x & 1 == 0` обчислюється як `x & (1 == 0)`, а не як перевірка молодшого
біта:

```cpp
int x = 2;
std::cout << (x & 1 == 0) << '\n';
std::cout << ((x & 1) == 0) << '\n';
```

Вивід — `0`, потім `1`. Clang попереджає про підозрілий пріоритет у першому
рядку; виправлення — поставити дужки навколо `x & 1`, як у другому рядку.

### 2. Спочатку група, потім індекс

`step()` читає байт за адресою `PC`, викликає `decode()` і розводить виконання
за старшим півбайтом:

| Група | Індекс | Інструкція |
|---|---:|---|
| `0x0_` | `0` | `HALT` |
| `0x0_` | `1` | `NOP` |
| `0x1_` | `0` | `ADD` |
| `0x1_` | `1` | `SUB` |
| `0x1_` | `2` | `AND` |
| `0x1_` | `3` | `OR` |
| `0x1_` | `4` | `XOR` |
| `0x1_` | `5` | `NOT` |
| `0x1_` | `6` | `SHL` |
| `0x1_` | `7` | `SHR` |
| `0x1_` | `8` | `INC` |
| `0x1_` | `9` | `DEC` |

Наприклад, для `0x16` зовнішній `switch` вибирає групу `0x1`, а внутрішній
знаходить індекс `6` і викликає `alu_shl`. Повний байт `0x16` більше не
потрібно окремо перевіряти у `switch`.


```txt
ember> reg a 1
ember> set 0 22
ember> set 1 22
ember> set 2 0
ember> step
ember> regs
PC=1 A=2 B=0 Z=0 N=0 C=0
ember> step
ember> regs
PC=2 A=4 B=0 Z=0 N=0 C=0
ember> step
ember> regs
PC=3 A=4 B=0 Z=0 N=0 C=0
ember> quit
```

Три `step` виконують `SHL`, `SHL`, `HALT`. Стани `PC=1 A=2`, `PC=2 A=4`
і `PC=3 A=4` показують, що декодер обробив групу `0x1_` для `SHL` і групу
`0x0_` для `HALT`.
